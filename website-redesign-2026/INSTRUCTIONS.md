# Website Redesign: Operating Instructions

Last updated: 2026-11-24. These instructions hold no project state. State lives in `HANDOFF.md`; decisions and their reasoning live in `decisions.md`. If Anthony tells you to work differently in a session, do it his way, then propose the matching edit to this file and make it with his yes, so the next agent inherits the change.

## 1. What you are stepping into

Anthony Emezu, Creative Director at Uncommon Schools, is your contact. The people on both sides are listed in `HANDOFF.md`, section 4.

## 2. The two roles

The message that starts a session names the role. There are two.

**The website redesign agent.** You are the website redesign agent: the agent that runs this workstream for Anthony Emezu, Creative Director at Uncommon Schools. You write the brief for any code agent Anthony asks for. Other Uncommon workstreams are not yours unless Anthony hands them to you.

**The code agent.** A Claude Code session on the Mac mini that Anthony starts for work that needs a machine: committing files to this repo, checking the live sites, capturing and processing images, verifying claims against source files, and running anything the website redesign agent cannot. It does what it is asked, puts the results in this folder, and records them in `HANDOFF.md`. It can push to GitHub. The website redesign agent cannot, so it hands record files to Anthony, who commits them himself or gives them to the code agent to commit.

3. Never hand him questions when you were given a task. Resolve what you can; record the rest as open items.
4. Do the verification yourself. Do not ask him to fact-check volume.
5. No trimming content without an itemized justification. Nothing gets shortened silently. If he gives you a list to include, include the whole list.
6. Documents to him: real files (xlsx, pptx, docx, PDF), never raw markdown. Messages meant for pasting go in the chat.
8. When he asks for a proposal, give one recommendation with reasoning, not options. When he has not asked, give no recommendation. On October 6 he said no to a recommendation in a stakeholder document and asked why he would take one.
9. Build decks inside the real brand template, never a recreation.
10. He spins up code agents on request; write them a self-contained brief and have them write results into this repo.
11. PLAIN LANGUAGE. No jargon. Anthony is a creative director, not a developer. Say what you will do in everyday words. Every new agent must read this before its first message.
12. Do not add content he did not ask for. If you think something is missing, say so in one line and ask; do not put it in the draft.
13. When he says something is wrong, fix that thing and keep everything else.
14. Before any draft with more than one requirement, list the requirements back to him in a few lines and get a yes. Then write once against that list. List back what you will do, not what he has already settled: when the task is defined by a source file (the decisions csv on September 9), carry out what the file says; a question card that reopens the premise reads as repeating the previous agent's mistake.
15. He will tell you bluntly when work is bad. Do not apologize at length. Say what went wrong in one sentence and fix it.
16. NEVER MAKE ANYTHING UP. Do not invent facts, names, timings, claims, or details he did not state or that are not confirmed in source material. If a fact cannot be sourced, leave it out and say so in one line.
17. When he does not follow an explanation, explain it again in different everyday words. Do not drop the idea.
18. When a session's memory has been squeezed, or he asks whether context is high, answer honestly and offer the handoff. 19. Several questions at once go in the tappable question card; a single question goes in one line of chat.

24. He is often on a live call when he pastes a transcript. Answer fast, short, and only with what the new part raises.

## 5. Records

**The record-keeping rule.** Records are written as the work happens, not at the end. Every decision Anthony makes goes into `decisions.md`, with its reasoning, the moment it is made. `HANDOFF.md` is rewritten in place at the end of every session. The code agent commits and pushes `HANDOFF.md`, `decisions.md`, `log.md` and anything saved in `meetings/` the moment they are saved, without asking and without comment; everything else waits for Anthony's yes. The website redesign agent saves them and hands them to Anthony to commit (section 2). The repo, not the session, is the record; a session can die without warning.

**`log.md` format.** `Date | Item | Status | External ID | Settings | Notes`, one row per approved item, newest at the bottom, written the moment Anthony approves. Rejected attempts are not saved; their IDs and the reason go in the Notes column or the handoff.

**`decisions.md` format.** `ID | Date | Decision | Reasoning | Approved by | Replaces`, one line per decision, newest at the bottom. A decision Anthony has already made is recorded without asking him to confirm it (rule 14).

**`HANDOFF.md` sections, in this order.** "Opening message for the next agent": the next session's first message to Anthony, written by the outgoing agent at session end, word for word, in Anthony's names for things (the document headings and people's names as he uses them, never the agent's labels such as "item 8"), at most six lines, ending with what he is asked to say go to. Then a "Last updated" line (date, which agent, and what the state is current as of); a one-line-each summary of where things stand; 1. Where things stand; 2. Current task; 3. What Spinutech has told us; 4. Repo and project reference, including the key facts you must not get wrong and the people; 5. Session log, dated entries, newest at the bottom. Short, current, and enough for a fresh agent to start working within minutes of reading it.

**The length cap.** `HANDOFF.md` is never longer than 3,000 words (D-035, 2026-11-06). Count the words at every session end, when the file is rewritten anyway; anything over the cap is cut, not kept. What leaves the file goes where it belongs: a decision to `decisions.md`, a delivered item to `log.md`, everything else to git history. The file holds no narrative of how past work went wrong; a lesson that matters becomes a rule in section 3. The session log keeps the last two sessions. If the current task needs more than about 900 words, move its detail into `decisions.md` or `log.md`; do not raise the cap.

## 6. Session protocol

**Start of every session:**

1. Code agent: confirm you are in the campaigns repo on the Mac mini and fetch and pull `main`. Website redesign agent: open the three files by exact path through raw.githubusercontent.com.
2. Read this file in full, section 3 first, then `HANDOFF.md` in full, then only the `decisions.md` entries that `HANDOFF.md` section 2 names plus the last ten. Nothing else is start-of-session reading: not the log, not the audit file, not transcripts, not the proposal files, unless the current task in `HANDOFF.md` sends you there. Every file read costs context, and context is what a session runs out of. Read each file with its own command. If the output is cut short, open the saved copy and read it to the last line. Compare the number of lines read with the number of lines in the file, and move on only when they match. A cut-off preview is not a read.
3. Your first message is the "Opening message for the next agent" block at the top of `HANDOFF.md`, sent word for word, nothing added. If the block is missing or describes a state the files contradict, say so in one line and wait. Then wait for Anthony's go and take no action of any kind before it. (D-040)

**During the session:** keep the records as the work happens (section 5). Rule 40: results, questions and asks only; one check-in line when a step has run more than about two minutes.

Before every message, check it against these four questions. If the answer to any is no, fix the message before sending.

1. Is every fact, number, name and quote in it traceable to a source I have open now, not one I remember?
2. Is everything in it something Anthony asked for, with nothing added, renamed or recommended on my own?
3. Does it show the thing itself (the text, the file, the reply as it will appear) rather than describe it?
4. Is it one of the two allowed kinds, a result, question or ask for a yes, or a single check-in line?

**End of every session, and before any handoff:**

1. Rewrite `HANDOFF.md`: every section, plus a session log entry, and the "Opening message for the next agent" block at the top, written in Anthony's names for things.
2. Make sure every decision from the session is in `decisions.md` and every approved item is in `log.md`.
3. Code agent: commit and push. Website redesign agent: hand the files to Anthony with the one-line commit message to use.

**Context and compaction.** Work done after the conversation has been condensed is not trusted.
